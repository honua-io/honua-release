# Original setup-key retirement

After genuine `prepare-studio-fixture` output exists, review its immutable
outcome object and saved-fixture reference into `setup_key_retirement` in the
campaign root configuration. Preserve the original native bootstrap operation,
liability basis and infrastructure/cleanup reservation IDs. `mode = "retire"`
requires `originalClaim = null`; actual issued setup key ID and immutable secret
version come from `issued_native_keys`, never from a caller-selected credential.
The retained accounting generation must remain funded and unresolved.

Use the checked saved-plan campaign deployment to create its dedicated private
task. Review the resulting `setup_retirement_handoff` byte-for-byte into
`certification/agent-e2e/setup-key-retirement-handoff.json`, then dispatch
`hosted-pilot-setup-retirement.yml` on protected trunk. Its permanent claim
permits one private launch. A missing launch acknowledgement cannot authorize
another launch. SQL, agent-worker, model and human browser credentials are not
injected into this task.

The task independently verifies original key issuance, saved fixture ownership,
original fixture HTTP evidence, immutable preparation artifacts and the stopped
preparation task. It reads the original setup key's effective permissions with
that same key before the independent original administrator revokes it. A fresh
administrator read must show the original key revoked and unable to
authenticate; that old immutable setup key must then receive **401** on the
same previously successful read. A scope denial (403) does not establish
revocation. The workflow retains actual STOPPED/exit evidence before evaluating
application success or reading its immutable receipt.

If revocation or receipt publication is interrupted, retain the original claim,
all task/state observations and all financial liabilities. First rerun the
original checked dispatcher when necessary to observe its existing task; it
cannot launch another task once the permanent claim exists. For read-only
recovery, review `mode = "observe"` and the original claim's exact `table`,
`key`, `bindingDigest`, `taskArn` and `taskDefinitionArn` into source, then use
the same saved-plan and checked-dispatch path. Recovery independently reads
that claim and its original immutable task configuration, verifies the original
before-effect positive control and revoke intent, and requires the original
task positively STOPPED. If ECS has aged out its task metadata, the retained
checked dispatcher's original terminal observation is mandatory; absence alone
is insufficient.

The recovery task performs only the independent revoked-status read and the old
key's 401 probe. It never repeats the revoke. It appends a new observation branch
and writes a separate immutable receipt, preserving the original task, setup
identity/version, operation, baseline and partial or completed evidence. Missing
original observations remain a blocker. No ledger is reset or allowance
replaced. Retirement proves neither a fresh model worker nor a successful case;
the original stopped task and immutable retirement receipt must be joined into
the subsequent independent case custody evidence.

If the original task stopped before issuing a revoke, or its wire outcome is
ambiguous and independent reads still show the original setup authority active,
review `mode = "resume"` with that exact original stopped task/claim. This is a
separate source-bound admission under the same retained global dispatch budget,
bootstrap reservations, immutable setup key/version and original deployment
`expiresAt`. Protocol 2 records a before-wire admission; missing admission is
classified as not issued, while a retained admission remains possibly issued.
Every earlier recovery task in the bounded original chain must also be
independently stopped. The deadline cannot be renewed by a new task/config.

A resume task freshly authenticates the exact old setup credential and
independently reads that same native key's active status/permissions before
admitting one revoke request. Native exact-ID revoke preserves its original
`RevokedAt` when repeated; `UpdatedAt` and a native revoke audit can repeat.
Possible earlier requests, audits and costs therefore remain unresolved in
append-only custody. An already revoked key is handled by reads only. Every
successful recovery still requires the independent revoked-status read and
old-key 401; it never mints, rotates or selects another credential, discards a
claim, resets a ledger or replaces original liabilities. A new task consumes
another original dispatch slot even when a previous acknowledgement was lost.
