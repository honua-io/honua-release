## 5. When the bill closes

Discharge, in order. Steps 2–4 all follow the candidate cut, and the manifest
must reach its final candidate state **before** the candidate-bound run, not
after it:

1. A green run of the lane dispatched against the **manifest-pinned** Lambda source digest — or against a manifest re-pinned to the certified artifact — with a receipt naming the exact source and ECR digests, executed serving assertions and cleanup outcomes → items 1 and 2. With item 5's pre-cut half already landed, the candidate cut is then unblocked.
2. Cut the candidate. Mirror the exact candidate's Lambda manifest into the release account, re-pin `awsLambdaEcrDigest` from that real mirror, and re-read `contractVersions` from the booted candidate → item 4. **The manifest is final at the end of this step.**
3. Re-run the lane against the exact candidate on that final manifest, with alias-shift upgrade and rollback through `AwsLambdaGitOpsDeployBackend`, serving verification before and after recovery, and full teardown → item 3.
4. Only then: `status: supported`, `qualification: passed`, and a `qualificationReceipt` whose `candidateManifestDigest` is `qualification_candidate_digest` over that same final manifest, and whose `url` is an immutable HTTPS location of **the step-3 receipt artifact itself** → item 5's remaining half completes and [release#282](https://github.com/honua-io/honua-release/issues/282) closes.

**Why item 4 precedes item 3.** `qualification_candidate_digest`
([`tools/validate_platform.py`](../tools/validate_platform.py), `:386-389`)
hashes the *entire* parsed manifest. Re-pinning `awsLambdaEcrDigest` or
`contractVersions` after the candidate-bound run therefore changes the digest
the receipt has to match, and the validator rejects the reference (`:428-429`).
Certifying first and re-pinning after would invalidate the receipt being bound;
the alternative is a second full certification run after the re-pin, which is
the same work done twice.

**Why the URL is the receipt, not the run page.** The
[operating envelope](2026.1-operating-envelope.md#5-aws-lambda-serverless-supported-target-and-limits)
requires the reference to point at the real full-bill receipt, but the validator
only checks that `url` has an HTTPS shape — scheme, host, non-empty path
(`:420-427`) — so nothing mechanical would stop a run page from passing while
identifying no evidence at all. A GitHub Actions run page is not the receipt
artifact: §6 shows the receipt only comes out of a separate artifact download,
and Actions artifacts expire on the repository's retention schedule. Publish or
archive `lambda-preview-receipt.json` at an immutable HTTPS URL and record that
URL; cite the run separately, as the reproduction path.

Any candidate-affecting change after step 3 invalidates the binding and requires
a fresh run and a fresh reference.
