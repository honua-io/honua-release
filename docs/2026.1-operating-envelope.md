## 3. What happens when a limit is reached

Configured controls and receipt-backed qualification are different facts. There
is no candidate-bound, topology-specific overload/recovery receipt here, so
graceful behavior at the complete operating envelope is **not qualified in
2026.1**. Use the protocol error returned by the supported SDK/CLI/MCP path;
do not assume every rejection is an HTTP rate-limit response or that a timeout
proves a mutation did not run.

| Limit or failure boundary | Current behavior and customer consequence |
| --- | --- |
| Request body with declared length above the configured cap | The pinned [limits middleware](https://github.com/honua-io/honua-server/blob/4ca8326f37b3225315033ee58e1a652e231992df/src/Honua.Server/Features/Infrastructure/Middleware/LimitsEnforcementMiddleware.cs) rejects before the handler with status **413**, message `Request payload exceeds maximum allowed size`, and the configured maximum in the detail. Its [protocol formatter](https://github.com/honua-io/honua-server/blob/4ca8326f37b3225315033ee58e1a652e231992df/src/Honua.Hosting/Features/Models/StandardErrorResponseFormatter.cs) selects the route's error envelope. This is a source-confirmed error contract, not a topology qualification receipt; tested payload ceiling: **not qualified in 2026.1**. |
| Cooperative handler observes the request deadline before response starts | The same middleware emits status **408**, `Request timeout`, with the configured duration in the detail. It cannot replace a response already started, and handlers must observe its deadline token. This conditional rejection contract is source-confirmed; complete topology/deadline qualification is **not qualified in 2026.1**. Maps is a known exception below. |
| OGC Processes admission evaluator refuses a submission | The pinned [process endpoint](https://github.com/honua-io/honua-server/blob/4ca8326f37b3225315033ee58e1a652e231992df/src/Honua.Protocols.OgcApi/Processes/ProcessEndpoints.cs) returns **503**, `Service unavailable`, the admission message, and `Retry-After`. Respect that delay through the supported client. This describes the rejection branch, not proof that admission is atomic or all GP transports share the same status; throughput/concurrency qualification: **not qualified in 2026.1**. |
| Map request deadline | **Undefined — tracked as [server#4284](https://github.com/honua-io/honua-server/issues/4284).** The documented end-to-end deadline is not propagated through the OGC Maps render path; connected work can continue beyond it. Database command timeouts do not establish a whole-request bound. Broken promise: the documented timeout control on a supported Maps workflow. |
| Vector-tile byte budget | **Undefined — tracked as [server#4287](https://github.com/honua-io/honua-server/issues/4287).** The advertised tile-size setting is not enforced as an output-byte cap; feature-count caps do not bound encoded attribute bytes. Broken promise: the published operator control. No measured maximum or memory-exhaustion incident is claimed. |
| GP admission under concurrent nodes/restart | **Undefined — tracked as [server#3853](https://github.com/honua-io/honua-server/issues/3853).** Admission reads active work separately from submission and rate buckets are process-local; do not rely on an atomic fleet-wide cap. | Storage exhaustion, output publication or durable-store loss | A complete graceful-rejection and recovery envelope is **not qualified in 2026.1**. Broken promise: the supported backup/recovery workflow must account for enabled job/workflow state. See the procedure caveat below. |

procedure is newly filed as server#4352. This page does not repair server behavior.

## 4. Backup procedure and recovery expectation

Follow the pinned [backup and restore runbook](https://github.com/honua-io/honua-server/blob/4ca8326f37b3225315033ee58e1a652e231992df/docs/guides/deploy/backup-and-restore.md)
for database and file handling, with the durable-substrate caveat below:

1. Inventory the deployment's durable state: PostgreSQL data/metadata, migration
   journal and transactional outbox; configured upload/attachment/output stores;
   Redis job queue, logs and workflow state where enabled. Record the exact image,
   configuration, backup identities and checksums. Keep secrets outside this record.
2. Before any backup capture, block new mutations and job submissions, drain
   in-flight requests/jobs to completion, then stop application replicas, workers,
   schedulers, outbox dispatchers and external writers across all nodes. Verify no
   writes remain to PostgreSQL, Redis or the file/object stores. If draining or
   quiescing fails, abort the backup; do not claim a consistent recovery set.
3. Keep that write boundary in place through the entire PostgreSQL `pg_dump`
   (custom format, tools matching the database major version) and the matching
   file-volume/object-store capture, including every enabled durable substrate
   from step 1. Bucket versioning/replication alone is not a consistent snapshot:
   record the exact object versions captured during this boundary. Verify readable
   archives, checksums and matching metadata/reference bytes before releasing the
   boundary and resuming writers. If an enabled substrate cannot be captured, the
   set is incomplete; see the Redis caveat below. Database WAL/PITR remains an
   infrastructure-owned option, not evidence of a tested Honua recovery objective.
4. Stop traffic and all writers again before restore, and keep them stopped until
   every matching store has been restored. Use `pg_restore` into a clean database
   and restore matching file/object state before starting the application. Ensure
   required extensions exist and select an image compatible with the restored
   migration journal. Startup may apply forward migrations.
5. Restart and verify readiness plus an actual supported-client catalog/feature
   journey. Check restored counts/checksums and referenced output bytes. For enabled
   workers, Redis and outbox, prove restart recovery through real runtime paths;
   a catalog browse alone does not establish job recovery or outbox delivery.

**Redis caveat:** the pinned runbook's store table says to exclude Redis from
restore planning, while its durable-job loss contract says Redis holds required
job/workflow state. Do not interpret that exclusion as a full-platform backup
procedure. AOF/reconnection guidance concerns restart resilience; it does not
prove recovery after primary-state destruction. Complete Redis/output/outbox
backup and recovery is **not qualified in 2026.1**, as documented by
[release#257](https://github.com/honua-io/honua-release/issues/257). The server
runbook correction is tracked as [server#4352](https://github.com/honua-io/honua-server/issues/4352).

**Substrate ruling (operator ruling A, 2026-09-12).** The 2026.1 soak and DR envelope is the
**local-docker substrate** — the single-tenant local Docker install (PostGIS, Redis and a local
file-storage volume) whose durable inventory the candidate manifest's `disasterRecovery` block now
resolves explicitly. Full-platform recovery for 2026.1 is qualified on that substrate and on
nothing else; **AWS qualification remains unqualified in 2026.1**, so no ECS, Lambda or other cloud
recovery claim follows from a local-docker receipt, and the cloud rows in this page's tables stand
unchanged. The producer is [`e2e/dr-drill/full_platform.py`](../e2e/dr-drill/README.md): one run
that, for every substrate the manifest declares enabled, writes durable state through a real
product surface, backs it up, destroys the primary state, restores into a verified-empty store,
restarts onto a different runtime instance, and re-reads identical state, with RPO and RTO measured
from those observations. `tools/validate_dr_receipt.py` recomputes the recovery window from the
receipt's own timestamps, so the measurement cannot be asserted. The rows below still read
**not qualified in 2026.1** because a receipt only qualifies this candidate once it is signed from
`refs/heads/trunk` and bound here; the mechanism existing is not the receipt existing.

| Recovery expectation | Receipt, topology and measured scope |
| --- | --- |
| Historical database restore | On the **local-docker PostgreSQL-only topology** above, the [DR receipt](../artifacts/dr-drill-local-docker/receipt.json) reports RPO **1,548 ms**, defined as last committed fixture to backup completion, and RTO **24,905 ms**, defined as destruction start to restored catalog journey green. It used custom-format dump/restore into a clean volume. These are observations for that tiny fixture and older image, not recovery guarantees. |
| Whole-platform restore, Redis job recovery, output bytes and post-restart outbox delivery | **Not qualified in 2026.1**. The historical receipt uses PostgreSQL job-shaped fixtures and captures checksums before restart; [the denominator finding](https://github.com/honua-io/honua-release/issues/257) explains the missing real substrates. |
| ECS, HA/failover, PITR, regional disaster, large datasets, backup frequency/retention and recovery SLO | **Not qualified in 2026.1**. Select and rehearse these with the deployment's infrastructure owner; no runbook default is a measured objective. |
| Upgrade and rollback | **Not qualified in 2026.1** in the [lock-derived upgrade table](SDK-SERVER-COMPATIBILITY.md#upgrade-edges). Reinstalling an older application does not undo a database migration. If that application cannot read the migrated schema and no verified reverse migration exists, returning to it requires a verified pre-upgrade backup restore. |

capacity or a certified topology. No AWS execution receipt is supplied here.

The receipt reference contains an HTTPS `url` and `candidateManifestDigest`:
`sha256:` plus SHA-256 of the parsed platform manifest serialized as UTF-8 JSON
with sorted keys, compact separators and unescaped Unicode
(`qualification_candidate_digest` in the validator). This binds every candidate
pin, including source/ECR Lambda digests and IaC revision, without hashing the
matrix that holds the reference. Any manifest change invalidates the binding.
The reference must point to the real full-bill receipt; reference validation
does not execute AWS assertions or replace the owning lanes' evidence checks.
No receipt reference is declared until that proof exists.
